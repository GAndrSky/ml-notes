11.5 SQL для ML

Датасет для модели — это запрос: одна строка на объект, признаки из прошлого, целевая переменная из будущего. Самая дорогая ошибка здесь не синтаксическая, а временная — утечка будущего в признаки.

Зачем это знать

В реальных проектах модель редко ломается из-за архитектуры и часто — из-за неправильно собранного датасета: признаки посчитаны с будущими данными, объекты потеряны при соединении, дубли после JOIN.

Что узнаешь
  • Собирать признаки на дату среза (point-in-time)
  • Строить целевую переменную из будущего окна
  • Находить утечки и считать признаки за разные окна условной агрегацией

Часть 5. Чтобы это не повторилось

Кирилла уволили, деньги частично вернули. Елена хочет модель, которая будет заранее помечать клиентов с высоким риском возврата. Модель обучат на истории до 1 октября 2025 года и проверят на том, что случилось после.

Дата среза и окна

Выберите момент времени — cutoff. Всё, что известно до него, можно использовать в признаках; то, что произошло после (в окне наблюдения), — только в целевой переменной. В продакшене модель будет работать именно так: в момент предсказания будущего ещё нет.

         признаки                 |        target
  ...───────────────────────── cutoff ───────────────────────...
       2025-01-01 … 2025-09-30    |   2025-10-01 … 2025-12-31

Для честной валидации берут несколько срезов (как rolling-origin валидация во временных рядах), а не один.

Признаки: одна строка на объект

Витрина признаков группирует события по объекту. Условная агрегация считает признаки за разные окна в одном проходе:

Проверки, которые стоит делать всегда: число строк равно числу объектов (нет дублей после JOIN), у признаков разумные диапазоны, нет признаков, которые вычисляются из target.

Target и утечки

Целевая переменная считается по окну после среза, а объекты без события должны получить 0 — поэтому начинают с полного списка объектов и присоединяют события через LEFT JOIN или EXISTS.

Типичные утечки в SQL: агрегат без фильтра по дате (сумма покупок «за всё время»), JOIN с таблицей, где значения перезаписываются задним числом (текущий статус вместо статуса на дату среза), признаки из полей, которые заполняются после события (дата возврата, сумма возврата). Симптом — слишком хорошие метрики на валидации.

Проверь себя

Вопросы для самопроверки

  1. Что такое point-in-time correct признаки?

    Признаки, посчитанные только по данным, которые были доступны в момент предсказания (до даты среза). Если признак использует события после среза, модель на обучении «видит будущее», метрики на валидации завышены, а в продакшене качество падает. В SQL это означает фильтр по дате события в каждом агрегате и соединение с версиями таблиц на нужную дату.

  2. Почему target строят от списка объектов, а не от таблицы событий?

    Если начать с таблицы событий (например, возвратов), в выборку попадут только объекты с событием, и у всех target будет 1. Нужен полный список объектов на дату среза, к которому событие присоединяется через LEFT JOIN или проверяется EXISTS: нет события — 0.

  3. Как JOIN может испортить витрину признаков?

    Связь «один ко многим» размножает строки: после соединения клиентов с заказами каждая строка клиента повторяется, и модель получает дубли, а агрегаты по «одной» стороне завышаются. Защита — агрегировать события до соединения (CTE на уровне объекта) и проверять, что число строк витрины равно числу объектов.

  4. Что такое условная агрегация и где она полезна?

    Агрегат по выражению с условием: SUM(CASE WHEN условие THEN x ELSE 0 END) или в SQLite просто SUM(условие). Позволяет одним проходом посчитать признаки за разные окна (за 30, 90, 365 дней), доли по категориям и сравнить «правильную» и «протекающую» версии признака.

6.9 RAG: Retrieval-Augmented Generation

RAG — не волшебный переключатель против галлюцинаций. Это система, которая находит доказательства, кладёт их в контекст и просит LLM ответить с опорой на них. Если retrieval провалился, генерация обычно тоже проваливается.

Почему важно

RAG решает ключевое ограничение LLM: устаревшие знания и hallucinations. Дать модели возможность «подглядывать» в документы через retrieval проще, чем переобучать модель каждый месяц.

Что узнаешь
  • Пайплайн retrieval: chunk → embed → index → retrieve → rerank
  • Cosine similarity в embedding space — как найти релевантные чанки
  • Hybrid search: dense (embedding) + sparse (BM25) — почему гибрид лучше
  • Evaluation: Recall@K и RAGAS — как оценить RAG систему
Нужно знать
  • LLM inference (6.7)
  • Vector embeddings
  • Поиск и индексирование

TL;DR

RAG объединяет поиск и генерацию: документы режут на chunks, эмбеддят, индексируют, по запросу находят релевантные chunks, переранжируют кандидатов, генерируют ответ с цитатами и оценивают и качество поиска, и обоснованность ответа.

Пайплайн

documents -> chunks -> embeddings -> vector index -> retrieve -> rerank -> generate -> verify
What each stage does
chunkstext unitsPassages small enough to retrieve and fit into model context.
embeddingsdense vectorsNumeric representation used for semantic similarity search.
indexsearch structureFAISS, Chroma, pgvector, or another vector database / ANN index.
reranksecond-stage scoringMore expensive model reorders a smaller candidate set.
verifygrounding checkChecks whether answer claims are supported by retrieved evidence.
Intuition: retrieval gives the model a temporary memory; generation turns that memory into a useful answer.
Analogy: open the right pages of a textbook before answering a question instead of answering from memory.

Chunking

Chunking — узкое место качества. Слишком мелкие chunks теряют контекст, слишком крупные размывают поиск и тратят окно контекста.

Частые стратегии

  • Окна фиксированной длины в токенах с overlap.
  • Chunking по абзацам или разделам.
  • Семантический chunking по границам тем.
  • Parent-child retrieval: ищем по мелким chunks, возвращаем более широкий контекст.

Что сохранять

  • Заголовок документа и иерархию разделов.
  • URL источника или путь к файлу.
  • Права доступа и метаданные.
  • Время или версию — для свежести.
Что это значит на практике
Плохой chunking создаёт нерешаемые задачи поиска. Если chunk содержит ответ, но без окружающего определения, генерация будет расплывчатой. Если chunk слишком широкий, эмбеддинг может совпасть не с той частью текста. Начни с простого chunking и вручную смотри найденные chunks.

Сходство эмбеддингов

cosine(q, d) = (q dot d) / (||q|| ||d||)
What the symbols mean
qquery embeddingVector representation of the user question.
ddocument embeddingVector representation of a chunk.
dotinner productMeasures alignment between two vectors.
||q||, ||d||normsNormalize vector lengths so direction matters more than magnitude.
Intuition: chunks pointing in a similar semantic direction to the query get higher scores.
Numeric example: if normalized vectors have dot product 0.82, they are much closer than a chunk with score 0.21.

Dense retrieval силён на перефразах. Sparse retrieval вроде BM25 силён на точных именах, ID, кодах ошибок и редких терминах. Гибридный поиск часто лучше каждого по отдельности.

Гибридный поиск и reranking

score = alpha * dense_score + (1 - alpha) * sparse_score
What the symbols mean
dense_scoreembedding matchSemantic similarity from vector search.
sparse_scorekeyword matchLexical score from BM25 or another sparse retriever.
alphamixing weightControls how much semantic vs keyword matching matters.
Intuition: combine meaning-based search with exact-word search so neither failure mode dominates.
Analogy: find a book by both topic similarity and exact title words.

Dense и BM25 scores живут в разных шкалах, поэтому перед смешиванием их нормируют (например, min-max внутри выдачи) или вместо взвешенной суммы используют Reciprocal Rank Fusion: score(d) = Σ 1/(k + rank_i(d)), k≈60.

Reranking обычно — второй этап: дёшево находим 50–200 кандидатов, затем cross-encoder или скорер на LLM оценивает лучших и формирует финальный top-k контекст.

Минимальный локальный скелет RAG

# What it does: builds a tiny embedding search loop with cosine similarity.
# Input shapes: docs=list[str], query=str
# Output shapes: top document strings ranked by similarity
import numpy as np

docs = [
    "KV-cache stores keys and values for previous tokens during decoding.",
    "Gradient checkpointing saves memory by recomputing activations.",
    "RAG retrieves external context before generating an answer.",
]

def toy_embed(text, dim=64):
    vec = np.zeros(dim, dtype=np.float32)
    for token in text.lower().split():
        vec[hash(token) % dim] += 1.0
    norm = np.linalg.norm(vec) + 1e-12
    return vec / norm

doc_emb = np.stack([toy_embed(d) for d in docs])
query = "How does retrieval augmented generation work?"
q_emb = toy_embed(query)

scores = doc_emb @ q_emb
top_idx = scores.argsort()[::-1][:2]

for i in top_idx:
    print(float(scores[i]), docs[i])

# Gotchas:
# 1. This toy embedding is only for mechanics; use real embedding models in practice.
# 2. Always inspect retrieved chunks before blaming the generator.
# 3. Python hash() for strings is randomized per process (PYTHONHASHSEED),
#    so this toy ranking can differ between runs; use a stable hash if you need reproducibility.

Оценка

Оценка RAG должна разделять поиск и генерацию. Если финальный ответ плохой, сначала спроси: нашла ли система нужные доказательства?

Метрики retrieval

  • Recall@K: нашлись ли доказательства где-то в top K?
  • MRR: насколько рано появляется первый релевантный chunk?
  • NDCG: стоят ли более релевантные chunks выше?
  • Context precision: какая доля найденного контекста полезна?

Метрики генерации

  • Корректность ответа относительно эталона.
  • Groundedness: подтверждаются ли утверждения контекстом.
  • Точность цитат.
  • Качество отказа, когда доказательств нет.
Recall@K = queries_with_relevant_chunk_in_top_K / total_queries

RAGAS — популярная библиотека для автоматической оценки RAG через LLM-судью: faithfulness (подтверждаются ли утверждения ответа контекстом), answer relevancy, context precision и context recall. Она удобна для регрессионных проверок, но LLM-судья сам ошибается, поэтому её оценки стоит периодически сверять с ручной разметкой.

What the symbols mean
Kretrieval cutoffNumber of chunks passed to evaluation or generation.
relevant chunkneeded evidenceA chunk that contains information required to answer the query.
total_querieseval set sizeNumber of labeled questions in the retrieval benchmark.
Intuition: before judging the LLM, check whether the answer was even available in context.
Numeric example: if 80 of 100 questions retrieve supporting evidence in top 5, Recall@5 is 0.80.

Как это ломается

Провалы retrieval
  • Chunk слишком мелкий или слишком крупный.
  • Модель эмбеддингов не подходит для языка домена.
  • Фильтры по метаданным отсекают нужный документ.
  • Индекс устарел после обновления документов.
Провалы генерации
  • LLM игнорирует контекст и отвечает из своих априорных знаний.
  • Ответ ссылается на нерелевантные chunks.
  • Промпт требует уверенности, которую модель не может обосновать.
  • В контексте противоречащие друг другу документы.
Правило для продакшена
Логируй запрос, ID найденных chunks, их scores, scores reranker-а, финальный промпт, ответ, цитаты, latency и обратную связь пользователя. Без этих логов отладка RAG превращается в гадание.

Проверь себя

Вопросы для самопроверки

  1. Что такое RAG и какую проблему LLM он решает?

    RAG (Retrieval-Augmented Generation) дополняет LLM внешней базой знаний. LLM страдают от hallucination (изобретают факты) и устаревших знаний (cutoff date). RAG: (1) retrieve — найти релевантные документы по запросу, (2) augment — добавить их в контекст, (3) generate — LLM отвечает с опорой на документы.

  2. Как работает dense retrieval (semantic search) в RAG?

    Документы и запрос кодируются в embeddings bi-encoder (например, SentenceBERT). Документы хранятся в vector DB (Faiss, Pinecone). При запросе: embed(query) → nearest neighbor search → top-k документов. Это семантически лучше BM25 для парафразированных запросов.

  3. Что такое chunking стратегия и почему она важна для RAG?

    Chunking — разбивка документов на фрагменты для индексирования. Маленькие chunks: высокая точность retrieval, но теряется контекст. Большие: больше контекста, но меньше релевантность. Оптимум зависит от embedding model и задачи. Sentence-level и paragraph-level chunking — популярные подходы.

  4. Что такое reranking в RAG pipeline и зачем он нужен?

    Первоначальный retrieval (ANN search) даёт top-k кандидатов. Reranker (cross-encoder) пересчитывает релевантность каждого кандидата к запросу более точно — он видит оба текста вместе. Это двухэтапный подход: быстрый recall первого этапа + точный precision второго.

Как закрепить тему: Retrieval-Augmented Generation

Блок связывает теорию с практикой: где применять идею, какие ошибки проверять и как развиваться дальше.

Когда применять

  • RAG — первый выбор для задач с актуальными или специализированными знаниями.
  • Начинай с BM25 baseline перед dense retrieval — иногда достаточно и быстрее.
  • Мониторь faithfulness метрику: генерирует ли модель только на основе retrieved контекста?

Типичные ошибки

  • Не разделять retrieval и generation ошибки при дебаггинге — они независимы.
  • Chunk size выбирать произвольно — экспериментируй на своей задаче.
  • Не учитывать context window limit при выборе top-k chunks.

Что тюнить / проверить

  • chunk_size и overlap — подбирай под embedding model и задачу.
  • top_k: больше = выше recall, но шум в контексте снижает precision.
  • Reranker threshold: баланс precision/recall для финального набора chunks.

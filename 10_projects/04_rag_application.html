10.4 Project: RAG Application

Собираем систему вопросов и ответов по документам: retrieval, цитаты, оценка и разбор ошибок.

Зачем это знать

RAG — самый востребованный паттерн для LLM-приложений в production. Умение построить его с нуля и оценить качество обязательно для LLM-инженера.

Что узнаешь
  • Построить RAG pipeline от индексации до генерации
  • Оценить качество через Ragas (faithfulness, relevance)
  • Оптимизировать chunk size и top-k под конкретную задачу
Нужно знать заранее
  • RAG (6.9)
  • Трансформеры (5.3)
  • Vector databases

TL;DR

RAG-приложение — это не «LLM плюс векторная база». Это система информационного поиска с генеративным слоем сверху. Большинство проблем качества — в chunking, recall поиска, reranking, сборке контекста и оценке.

Что должно получиться

  • Генерация ответа с цитатами.
  • Evaluation-набор с метриками retrieval и качества ответа.

Пайплайн

documents -> chunks -> embeddings -> vector index -> top-k retrieval -> context -> LLM answer + citations

На что обратить внимание: если ответ неверный, сначала проверь, нашёлся ли нужный chunk. Генерация не исправит отсутствующие доказательства.

Цель retrieval

score(q, d_i) = cosine(embed(q), embed(d_i))
What the symbols mean
qqueryUser question or rewritten search query.
d_ichunkOne candidate document fragment.
embedembedding modelMaps text into a vector space where similarity approximates relevance.
cosinesimilarityCompares vector directions, usually after normalization.
Intuition: retrieval finds chunks whose meaning points in the same direction as the question.
Analogy: library search returns pages most semantically aligned with your question.

Игрушечный retrieval, который можно запустить

# What it does: toy vector retrieval with cosine similarity
# Input shapes: query=(d,), docs=(N,d)
# Output shape: top indices=(k,)
import numpy as np

def normalize(x):
    return x / (np.linalg.norm(x, axis=-1, keepdims=True) + 1e-9)

docs = np.array([[1,0], [0,1], [0.8,0.2]], dtype=float)
query = np.array([1,0.1], dtype=float)
scores = normalize(docs) @ normalize(query[None, :]).T
top = np.argsort(scores[:, 0])[::-1][:2]
print(top, scores[top, 0])
# Gotchas: semantic embeddings are not magic; evaluate recall on real questions.

Частые ошибки

  • Резать на chunks фиксированной длины, не учитывая границы разделов.
  • Смотреть только на качество ответа, игнорируя recall поиска.
  • Набивать слишком много контекста, размывая фокус ответа.
  • Не хранить метаданные — тогда цитаты невозможны.
Пошагово Пайплайн RAG-запроса
1 /
Шаг 01

Эмбеддинг запроса

Пришёл запрос пользователя. Эмбеддим его той же моделью, что и документы при индексации: другая модель даёт несовместимое векторное пространство, где cosine similarity бессмысленна.

Шаг 02

Векторный поиск

Достаём из индекса top-K chunks по cosine similarity, обычно K = 5–20. Больше chunks — выше recall, но длиннее промпт и дороже LLM. Начни с K = 10 и подстрой по метрикам recall.

Шаг 03

Reranking

Передаём запрос и найденные chunks в cross-encoder, переранжируем по оценке релевантности и оставляем top-3. Cross-encoder медленнее, но заметно точнее bi-encoder в оценке релевантности, потому что обрабатывает запрос и документ вместе.

Шаг 04

Сборка контекста

Добавляем найденные chunks в промпт с метаданными источника (документ, страница, раздел) и их ID, чтобы генератор мог на них ссылаться. Общий контекст должен помещаться в окно LLM с запасом на ожидаемую длину ответа.

Шаг 05

Генерация с цитатами

LLM генерирует ответ, опираясь на переданный контекст, и возвращает ответ вместе с цитатами. Оценивай groundedness: подтверждаются ли утверждения ответа найденными chunks? Неподтверждённые утверждения — галлюцинации.

Что ломается без этого

Разные модели эмбеддингов для индексации и запросов делают поиск случайным: cosine similarity между разными пространствами бессмысленна. Система возвращает документы с высоким «сходством» векторов, никак не связанные с запросом по смыслу. Все последующие метрики качества падают по причинам, которые трудно найти, если не проверить согласованность модели эмбеддингов первым делом.

Проверь себя

Вопросы для самопроверки

  1. Как выбрать embedding model для RAG системы?

    Критерии: (1) размерность — больше не всегда лучше (768 vs 1536), (2) benchmark на domain-specific задачах (MTEB leaderboard), (3) поддержка русского языка при необходимости, (4) inference speed, (5) максимальная длина контекста. BAAI/bge и E5 — сильные общие модели.

  2. Что такое chunking overlap и зачем он нужен?

    Overlap: соседние chunks делят несколько предложений. Без overlap релевантная информация может оказаться на стыке chunks — оба chunk частично «половинчаты» и ни один не релевантен полностью. Overlap 10-20% предотвращает это, добавляя контекст на краях.

  3. Как оценить качество RAG системы?

    Метрики: (1) Retrieval: precision@k, recall@k, nDCG (насколько релевантны найденные chunks). (2) Generation: faithfulness (нет ли hallucinations вне retrieved context), answer relevance, context relevance. Ragas — библиотека для автоматической оценки RAG по этим метрикам. Faithfulness можно проверять и LLM-as-judge или NLI-моделью (следует ли утверждение из контекста). Но сначала всегда смотри retrieval: если нужный chunk не найден, ответ будет неверным при любой LLM.

  4. Что такое HyDE (Hypothetical Document Embeddings) и как он улучшает retrieval?

    HyDE: вместо поиска по исходному запросу генерируем LLM гипотетический ответ, затем ищем документы по embedding этого ответа. Гипотетический ответ семантически ближе к реальным документам, чем короткий вопрос. Улучшает recall, особенно для абстрактных или сложных запросов.

  5. Почему документы и запросы нужно эмбеддить одной и той же моделью?

    Модель эмбеддингов учит своё векторное пространство, где похожие тексты геометрически близки. У разных моделей разные пространства: векторы из модели A и модели B не имеют общей системы координат, cosine similarity между ними бессмысленна, и поиск становится случайным. Индексируй и запрашивай одной и той же версией модели (при смене модели — переиндексация).

  6. Чем bi-encoder отличается от cross-encoder в retrieval?

    Bi-encoder эмбеддит запрос и документ независимо и сравнивает векторы скалярным произведением — быстро, документы можно проиндексировать заранее, но точность ниже. Cross-encoder получает запрос и документ одним входом и выдаёт оценку релевантности — гораздо точнее, потому что моделирует их взаимодействие, но для каждой пары нужен отдельный forward, и заранее ничего не проиндексируешь. Поэтому bi-encoder — для recall по всей базе, cross-encoder — для reranking top-кандидатов.

Как закрепить тему: RAG Приложение

Блок связывает теорию с практикой: где применять идею, какие ошибки проверять и как развиваться дальше.

Когда применять

  • Начинай с BM25 retrieval + GPT-4 generation — простой baseline для оценки потолка.
  • Ragas или LLM-as-judge обязателен для оценки faithfulness.
  • Мониторь, какие запросы не находят релевантных документов — это сигнал о coverage gap.

Типичные ошибки

  • Не разделять retrieval и generation ошибки при дебаггинге.
  • Не тестировать на adversarial запросах (вне knowledge base, противоречивые вопросы).
  • Не учитывать context window при выборе chunk_size × top_k.

Что тюнить / проверить

  • chunk_size: 200-500 слов для большинства задач.
  • top_k: 3-5 для начала, увеличивай при низком recall.
  • Temperature LLM: снижай для factual задач (0.1-0.3).

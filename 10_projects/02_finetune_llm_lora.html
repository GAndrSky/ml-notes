10.2 Project: Fine-tune an LLM with LoRA

Собираем полный пайплайн parameter-efficient fine-tuning: готовим instruction-датасет, обучаем LoRA-адаптеры, оцениваем поведение, экспортируем артефакты и документируем failure modes.

TL;DR

LoRA замораживает базовую модель и обучает маленькие low-rank матрицы обновления. Проект учит практическому workflow: качество данных, формат промпта, где ставить адаптеры, гиперпараметры, оценка и безопасный экспорт.

  • Не утверждай, что модель выучила факты по 50 примерам.

  • Держи отложенный validation-набор промптов.

Основная идея

W' = W + DeltaW, where DeltaW = B A and rank(DeltaW) << rank(W)
What the symbols mean
Wfrozen base weightOriginal pretrained model matrix, not updated during LoRA training.
DeltaWlearned updateTask-specific change added to the base weight.
Adown projectionSmall matrix that maps from original dimension into rank r.
Bup projectionSmall matrix that maps from rank r back to output dimension.
rLoRA rankControls adapter capacity; common values are 4, 8, 16, 32, 64.
Intuition: instead of changing all model weights, learn a small structured correction in the directions that matter for the task.
Analogy: keep the whole book unchanged and add a thin task-specific annotation layer.
trainable_params = r * (d_in + d_out) instead of d_in * d_out
Numeric example
d_ininput widthFor example 4096 in a transformer projection.
d_outoutput widthFor example 4096 in the same projection.
rrankIf r=16, trainable params are 16*(4096+4096)=131k instead of 16.7M.
Intuition: the trainable part becomes tiny compared with the original matrix.
Practical meaning: you can fine-tune larger models on smaller GPUs because optimizer state is stored only for adapters.

Этап 1 — формат датасета

В instruction tuning формат данных часто важнее rank или learning rate. Примеры должны быть единообразными и совпадать с тем, как ты будешь промптить модель на inference.

# What it does: creates a tiny instruction dataset in chat format.
# Input shapes: list[dict] with instruction/input/output strings
# Output shapes: Hugging Face Dataset with one text column
from datasets import Dataset

rows = [
    {
        "instruction": "Explain gradient descent to a beginner.",
        "input": "",
        "output": "Gradient descent repeatedly moves parameters in the direction that reduces loss."
    },
    {
        "instruction": "Convert the note into three bullet points.",
        "input": "Adam keeps moving averages of gradients and squared gradients.",
        "output": "- Adam tracks gradient direction\n- Adam tracks gradient scale\n- Adam adapts step sizes per parameter"
    },
]

def format_example(row):
    return {
        "text": (
            "### Instruction:\n" + row["instruction"].strip() +
            "\n\n### Input:\n" + row["input"].strip() +
            "\n\n### Response:\n" + row["output"].strip()
        )
    }

dataset = Dataset.from_list([format_example(row) for row in rows])
print(dataset[0]["text"])

# Gotchas:
# 1. Keep train and inference prompt formats consistent.
# 2. Do not mix contradictory answer styles in a tiny dataset.

Этап 2 — настройка LoRA

# What it does: wraps a causal LM with LoRA adapters.
# Input shapes: tokenized batch input_ids=(B,L), labels=(B,L)
# Output shapes: model returns loss=scalar and logits=(B,L,V)
from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model, TaskType

model_name = "TinyLlama/TinyLlama-1.1B-Chat-v1.0"
tokenizer = AutoTokenizer.from_pretrained(model_name)
# separate pad token: DataCollatorForLanguageModeling masks every pad id in labels,
# so pad == eos would hide EOS and the model would never learn to stop
tokenizer.pad_token = tokenizer.unk_token or tokenizer.eos_token

model = AutoModelForCausalLM.from_pretrained(model_name, device_map="auto")

lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    r=16,
    lora_alpha=32,
    lora_dropout=0.05,
    target_modules=["q_proj", "k_proj", "v_proj", "o_proj"],
)

model = get_peft_model(model, lora_config)
model.print_trainable_parameters()

# Gotchas:
# 1. target_modules depend on model architecture; inspect module names if this fails.
# 2. Larger r increases capacity but also memory and overfitting risk.

Этап 3 — обучение

# What it does: trains LoRA adapters with Hugging Face Trainer.
# Input shapes: dataset["text"] tokenized to input_ids=(B,L)
# Output shapes: saved adapter files in output_dir
import torch
from transformers import TrainingArguments, Trainer, DataCollatorForLanguageModeling

def tokenize(batch):
    return tokenizer(
        [t + tokenizer.eos_token for t in batch["text"]],  # EOS teaches the model to stop
        truncation=True,
        max_length=512,
        padding=False,
    )

tokenized = dataset.map(tokenize, batched=True, remove_columns=["text"])
collator = DataCollatorForLanguageModeling(tokenizer=tokenizer, mlm=False)

args = TrainingArguments(
    output_dir="outputs/lora-ml-notes-demo",
    per_device_train_batch_size=1,
    gradient_accumulation_steps=8,
    learning_rate=2e-4,
    num_train_epochs=3,
    logging_steps=1,
    save_strategy="epoch",
    fp16=False,
    bf16=torch.cuda.is_available() and torch.cuda.is_bf16_supported(),
    report_to=[],
)

trainer = Trainer(
    model=model,
    args=args,
    train_dataset=tokenized,
    data_collator=collator,
)
trainer.train()
model.save_pretrained("outputs/lora-adapter")
tokenizer.save_pretrained("outputs/lora-adapter")

# Gotchas:
# 1. bf16 is enabled only on GPUs that support it; fp16 needs loss scaling, use with care.
# 2. Tiny datasets can quickly overfit style without improving task ability.
# 3. Pad token must differ from EOS: the collator sets labels of all pad ids to -100.
#    If the tokenizer has no unk token, add a dedicated one: tokenizer.add_special_tokens(
#    {"pad_token": ""}) and model.resize_token_embeddings(len(tokenizer)).
# 4. This collator computes loss on the instruction too; to train only on the response,
#    mask prompt tokens with -100 (e.g., TRL completion-only collator / SFTTrainer).

Этап 4 — оценка до и после

Не оценивай по одному красивому ответу. Собери небольшой фиксированный набор промптов и сравни базовую и адаптированную модель с одинаковыми настройками декодирования.

Качественная оценка

  • Следует ли модель целевому формату?
  • Не галлюцинирует ли неподтверждённые детали?
  • Сохранила ли полезные способности базовой модели?
  • Не стала ли слишком повторяющейся или слишком краткой?

Количественная оценка

  • Held-out loss на validation-промптах.
  • Точное соответствие формату для структурированных выходов.
  • Человеческие предпочтения между ответами до/после.
  • Latency и память, если адаптер используется в serving.
# What it does: generates a response from the LoRA-adapted model.
# Input shapes: prompt tokens input_ids=(1,L)
# Output shapes: generated tokens=(1,L_new)
import torch

prompt = "### Instruction:\nExplain LoRA in two sentences.\n\n### Input:\n\n### Response:\n"
inputs = tokenizer(prompt, return_tensors="pt").to(model.device)

with torch.no_grad():
    generated = model.generate(
        **inputs,
        max_new_tokens=80,
        do_sample=False,
        temperature=None,
        pad_token_id=tokenizer.eos_token_id,
    )

print(tokenizer.decode(generated[0], skip_special_tokens=True))

# Gotchas:
# 1. Use identical decoding settings when comparing base and adapted models.
# 2. Greedy decoding is stable for tests; sampling is useful for product behavior checks.

Проверь себя

Вопросы для самопроверки

  1. Какой минимальный объём данных нужен для эффективного LoRA fine-tuning?

    Для специализации на стиль или формат ответа — 100-500 примеров достаточно. Для обучения предметным знаниям — от 1k. Для instruction following в новой области — 1k-10k. Качество важнее количества: разнообразные, чистые примеры > большой зашумлённый датасет.

  2. Как оценить качество fine-tuned LLM без человеческой разметки?

    LLM-as-judge: промптить сильную модель (GPT-4/Claude) оценить ответ по критериям (точность, безопасность, стиль). MT-bench и Alpaca Eval — стандартные benchmarks. Также автоматические метрики: ROUGE (для summarization), pass@k (для code generation), Exact Match (для QA).

  3. Что такое catastrophic forgetting при fine-tuning LLM?

    Catastrophic forgetting: при обучении на узкой задаче модель «забывает» общие знания. Симптомы: деградация на benchmarks, потеря instruction following. LoRA снижает риск (веса заморожены). Также помогает: добавление general data в training mix, низкий lr, небольшое число эпох (1-3).

  4. Как выбрать base model для fine-tuning под конкретную задачу?

    Критерии: (1) размер — баланс качества и inference cost, (2) лицензия (Llama — commercial use с условиями, Mistral — Apache 2.0), (3) языковая поддержка, (4) context length, (5) уже ли обучена на похожей задаче (меньше fine-tuning данных нужно). Начинают с меньшей модели — быстрее итерации.

  5. Как rank LoRA связан с числом обучаемых параметров?

    На слой: r · (d_in + d_out). Для проекции 4096×4096 при r=16: 16 · (4096 + 4096) = 131 072 параметра вместо 16.7M при полном fine-tuning. Удвоение rank удваивает число обучаемых параметров; rank задаёт размерность подпространства обновления.

  6. Почему для большинства задач LoRA предпочтительнее полного fine-tuning?

    Градиенты и optimizer state нужны только для матриц адаптера — это на порядки меньше памяти на эти части (сами базовые веса всё равно лежат в памяти; QLoRA дополнительно квантует их). Базовые веса заморожены, что снижает (но не исключает) catastrophic forgetting. Несколько адаптеров под разные задачи делят одну базовую модель. Для многих задач полезное обновление действительно хорошо приближается low-rank.

  7. Что будет, если поставить слишком большой rank?

    Большой rank (например, r > 64) без пропорционально большего датасета ведёт к переобучению: train loss падает, а качество на отложенных данных ухудшается — адаптер запоминает примеры. Следи за validation loss и используй early stopping. Кроме того, большой rank съедает выигрыш LoRA по памяти.

Пошагово Настройка LoRA fine-tuning
1 /
Шаг 01

Выбираем target modules

Обычно это q_proj и v_proj в attention, иногда все линейные слои. Больше модулей — больше ёмкость и память. Начни узко и расширяй, если модель недоучивается.

Шаг 02

Выбираем rank r

Начни с r=8 или r=16. Меньший rank — меньше параметров и сильнее регуляризация; больший — больше ёмкость, но выше риск переобучения на малых данных. Обучаемых параметров на слой: r · (d_in + d_out).

Шаг 03

Выбираем alpha

Alpha масштабирует обновление LoRA: адаптер добавляет (alpha / r) · B A к замороженному весу. Частое правило — alpha = 2·r (например, r=16, alpha=32): тогда множитель alpha/r = 2 не меняется при переборе rank, и learning rate не приходится подбирать заново.

Шаг 04

Замораживаем базовую модель

Обучаться должны только матрицы LoRA. Проверь: sum(p.numel() for p in model.parameters() if p.requires_grad) или model.print_trainable_parameters(). В PEFT заморозку делает get_peft_model, но всегда убеждайся, что число обучаемых параметров совпадает с ожидаемым.

Шаг 05

Слияние и сохранение

После обучения LoRA-веса можно влить в базовую модель: model = model.merge_and_unload(). Это убирает overhead адаптера на inference. Несмёрженный адаптер сохрани, если хочешь потом переключать задачи.

Что ломается без этого

Если не заморозить базовую модель, LoRA теряет смысл: получается полный fine-tuning с лишними параметрами и большей памятью. Optimizer state растёт до всех параметров модели, преимущество по памяти исчезает, адаптер становится бесполезной надстройкой, а риск catastrophic forgetting заметно растёт.

Как закрепить тему: Fine-tune LLM с LoRA

Блок связывает теорию с практикой: где применять идею, какие ошибки проверять и как развиваться дальше.

Когда применять

  • Начинай с маленькой модели (7B) на маленьком датасете — быстрые итерации.
  • Evaluation обязателен: без него не знаешь, что обучение помогло.
  • DPO после SFT часто улучшает стиль ответов без потери качества.

Типичные ошибки

  • Обучать без evaluation pipeline — нельзя определить overfitting.
  • Использовать слишком высокий lr при LoRA — веса быстро уходят в catastrophic forgetting.
  • Не проверять degeneration на базовых бенчмарках после fine-tuning.

Что тюнить / проверить

  • LoRA rank r: начинай с 16, увеличивай при недоученности.
  • Target modules: q_proj + v_proj минимум, добавляй k_proj + up/down proj при необходимости.
  • Число эпох: 1-3, больше — риск overfitting и forgetting.

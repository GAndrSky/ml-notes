TL;DR

Успех на Kaggle — это меньше про перебор случайных моделей и больше про дисциплину валидации. Если локальная валидация не предсказывает движение leaderboard, любое «улучшение» под подозрением.

Workflow

  1. Сначала прочитай метрику и формат сабмита.
  2. Сделай «тупой» baseline.
  3. Построй валидацию без утечек.
  4. Проведи EDA с фокусом на target, пропуски, группы, время и утечки.
  5. Учи простые устойчивые модели раньше сложных ансамблей.
  6. Логируй эксперименты и сравнивай локальный score с public leaderboard.
  7. Ансамблируй только модели с разными ошибками.

Валидация — это и есть проект

trust = correlation(local_cv_score, leaderboard_score)

Если локальная CV раз за разом растёт, а leaderboard падает, скорее всего, сплит неверный. Для временных рядов используй разбиение по времени, для данных пользователей/товаров — по группам, для дублирующихся сущностей — по сущности, а не по строкам.

Скелет валидации, который можно запустить

# What it does: leakage-safe grouped cross-validation skeleton
# Input shapes: X=(N,d), y=(N,), groups=(N,)
# Output shape: fold scores=(K,)
import numpy as np
from sklearn.model_selection import GroupKFold
from sklearn.metrics import root_mean_squared_error
from sklearn.ensemble import RandomForestRegressor

X = np.random.randn(100, 5)
y = X[:, 0] * 2 + np.random.randn(100) * 0.1
groups = np.repeat(np.arange(20), 5)

scores = []
for train_idx, valid_idx in GroupKFold(n_splits=5).split(X, y, groups):
    model = RandomForestRegressor(n_estimators=50, random_state=0)
    model.fit(X[train_idx], y[train_idx])
    pred = model.predict(X[valid_idx])
    scores.append(root_mean_squared_error(y[valid_idx], pred))
print(scores, np.mean(scores))
# Gotchas: choose split strategy before feature engineering; never fit preprocessing on validation data.

Чеклист feature engineering

  • Индикаторы пропусков, если пропуск сам несёт информацию.
  • Агрегаты по target — только внутри фолдов.
  • Временные и lag-признаки для временных данных.
  • Count/frequency encoding для категориальных признаков.
  • Эмбеддинги текста/изображений, если данные мультимодальные.

Частые ошибки

  • Использовать public leaderboard как валидацию.
  • Утечка target через глобальный target encoding или предобработку на всех данных.
  • Менять много вещей сразу и не знать, что помогло.
  • Переобучаться под public leaderboard слишком частыми сабмитами.

Шаг 01

Сначала EDA

Пойми данные, поищи утечки и проверь сдвиг распределения между train и test до того, как писать код модели. Утечка, найденная рано, экономит дни работы; сдвиг распределения объясняет, почему сильная локальная модель проседает на leaderboard.

Шаг 02

Валидация без утечек

Для классификации используй StratifiedKFold, чтобы в каждом фолде сохранялась доля классов (для регрессии — обычный KFold или KFold по бинам target). Для временных рядов — разбиение по времени, для сгруппированных данных (одна сущность в нескольких строках) — GroupKFold. Никогда не используй метки или статистики test в feature engineering. Зафиксируй схему валидации до работы с признаками.

Шаг 03

Baseline + feature engineering

Табличные данные: сначала baseline на gradient boosting. NLP: предобученный трансформер. CV: предобученная CNN или ViT. Получи число на leaderboard до feature engineering: признаки поверх плохого baseline — потеря времени; занимайся ими, когда схема валидации заслуживает доверия.

Шаг 04

Ансамблирование

Усредняй предсказания разных моделей. Чем ниже корреляция их ошибок, тем больше выигрыш от ансамбля. Разнообразие дают разные алгоритмы (GBM vs NN vs линейные), разные наборы признаков и, слабее, разные seed-ы. Ансамбль почти одинаковых моделей почти ничего не даёт.

Шаг 05

Финальная стадия: pseudo-labeling

Pseudo-labeling на уверенных предсказаниях test может дать прирост в последние дни: учим модель на train плюс уверенные предсказания test как на размеченных данных (берём только самые уверенные, например top 10–20%). Проверь, что правила соревнования это разрешают, и следи, чтобы псевдометки не попадали в валидационные фолды — иначе CV станет оптимистичной.

Что ломается без этого

Валидация на случайном сплите вместо разбиения по времени для временных рядов приводит к утечке будущего: модель видит в train паттерны, которых при реальном прогнозе ещё нет, и CV получается заметно лучше leaderboard. Это самая частая причина, почему сильная локальная CV не переносится на leaderboard в соревнованиях по временным рядам.

Оцени понимание темы

Разбор ключевой формулы

competition score = feature quality + validation quality + ensemble quality
Что означают символы
feature qualityкачество признаковнасколько хорошо engineered features раскрывают signal в данных.
validation qualityкачество валидациинасколько локальная CV честно предсказывает leaderboard/generalization.
ensemble qualityкачество ансамблянасколько модели дают полезную diversity, а не дублируют ошибки друг друга.
Интуиция: в Kaggle главный актив — не одна модель, а хороший validation loop и disciplined experimentation.
Числовой пример: leaderboard часто улучшается не от новой архитектуры, а от честного CV и нескольких слабо коррелированных моделей.

Упражнения: Kaggle Walkthrough

[Foundational] Leakage audit

Назови три типичных источника leakage в табличной competition.

Решение. (1) Признаки из будущего: агрегаты, посчитанные по всему периоду (средняя сумма покупок клиента за весь датасет), поля, заполняемые после события (дата закрытия заявки, статус возврата). (2) Target encoding и масштабирование на всех данных до разбиения, включая test. (3) Идентификаторы и порядок: ID, растущий со временем, имя файла или порядок строк, коррелирующий с target; дубликаты одних и тех же сущностей в train и test (одного клиента/пациента). Как ловить: модель на одном признаке — подозрительно сильный признак проверить; adversarial validation (классификатор train vs test) — признаки, по которым их легко отличить; сравнение распределений признаков во времени.

[Intermediate] CV design

Подбери split strategy для временной, grouped и обычной табличной competition.

Решение. Временная (прогноз продаж): разбиение по времени — TimeSeriesSplit или скользящее окно, validation всегда позже train, при необходимости с зазором (gap) на длину горизонта; признаки-лаги считаются только из прошлого. Grouped (несколько строк на клиента/пациента/сессию): GroupKFold (или StratifiedGroupKFold), чтобы одна сущность не попала одновременно в train и validation — иначе модель запоминает сущность. Обычная табличная (независимые строки): StratifiedKFold для классификации, KFold (или по бинам target) для регрессии, 5 фолдов, несколько seed-ов для оценки разброса. Во всех случаях схема CV должна повторять разницу между train и test в соревновании — проверь adversarial validation, отличается ли test от train.

[Hard] Ensemble plan

Опиши, как оценить, стоит ли добавлять ещё одну модель в ensemble.

Решение. (1) Сохрани OOF-предсказания всех моделей с одинаковым разбиением на фолды. (2) Посчитай корреляцию OOF-предсказаний новой модели с текущим ансамблем: при корреляции 0.99 выигрыша почти не будет. (3) Оцени ансамбль с новой моделью и без неё на OOF (простое среднее или веса, подобранные на OOF с кросс-валидацией самих весов), и посмотри на разброс по фолдам: прирост должен быть больше стандартного отклонения между фолдами. (4) Проверь, что прирост виден и на public LB — но не выбирай по нему. (5) Учитывай стоимость: время инференса и сложность воспроизведения. Правило: добавляй модель, если она даёт устойчивый прирост OOF на большинстве фолдов и вносит разнообразие (другой алгоритм, признаки, представление данных).

[Foundational] Разбор соревнования

Выбери датасет Kaggle и выпиши метрику, target, формат сабмита и вероятные риски утечки.

Решение. Пример: Titanic (Kaggle). Target: Survived (0/1). Метрика: accuracy — значит, нужен порог, а не вероятности; при дисбалансе 62/38 baseline «все погибли» даёт ~0.62. Сабмит: CSV с PassengerId и Survived для 418 строк test. Риски утечки: (1) семьи и группы по одному билету разнесены между train и test — признаки «выжили ли родственники» (через Ticket/фамилию) очень сильны, но должны считаться только по train-меткам; (2) заполнение пропусков Age по всем данным (train + test) — мелкая утечка распределения; (3) public LB считается лишь по части test — легко переобучиться на нём. Такой разбор стоит делать до первой строки модели.

[Intermediate] Три вида KFold

Реализуй KFold, StratifiedKFold и GroupKFold на игрушечном датасете и объясни, когда каждый из них ломается.

Решение. Код показывает, когда каждая схема ломается: KFold на данных с дисбалансом даёт фолды с разной долей позитивов; StratifiedKFold не знает о группах и пускает одну сущность в train и validation; GroupKFold держит группы раздельно.

import numpy as np
from sklearn.model_selection import KFold, StratifiedKFold, GroupKFold

rng = np.random.default_rng(0)
n = 60
y = (rng.random(n) < 0.15).astype(int)          # 15% positives
groups = np.repeat(np.arange(15), 4)            # 15 users x 4 rows each
X = np.zeros((n, 1))

for name, cv in [("KFold", KFold(5, shuffle=True, random_state=0)),
                 ("StratifiedKFold", StratifiedKFold(5, shuffle=True, random_state=0)),
                 ("GroupKFold", GroupKFold(5))]:
    pos, leaked = [], 0
    args = (X, y, groups) if name == "GroupKFold" else (X, y)
    for tr, va in cv.split(*args):
        pos.append(round(float(y[va].mean()), 2))
        leaked += len(set(groups[tr]) & set(groups[va]))
    print(f"{name:16} positive share per fold {pos}  users in both train and val: {leaked}")

[Intermediate] Target encoding

Сделай target encoding внутри фолдов и сравни его с «протекающим» глобальным вариантом.

Решение. Сравниваем на признаке-шуме: у категории нет связи с target, поэтому честная оценка должна быть ≈ 0.5 AUC. Глобальный encoding «видит» метку объекта и показывает ложный сигнал.

import numpy as np
from sklearn.model_selection import KFold
from sklearn.metrics import roc_auc_score

rng = np.random.default_rng(0)
n = 2000
cat = rng.integers(0, 400, n)          # high-cardinality category, ~5 rows each
y = rng.integers(0, 2, n)              # target independent of the category

def global_encoding(cat, y):
    means = {c: y[cat == c].mean() for c in np.unique(cat)}
    return np.array([means[c] for c in cat])

def oof_encoding(cat, y, k=5, prior_weight=10):
    enc, prior = np.zeros(len(y)), y.mean()
    for tr, va in KFold(k, shuffle=True, random_state=0).split(cat):
        for c in np.unique(cat[va]):
            m = cat[tr] == c
            enc[va[cat[va] == c]] = (y[tr][m].sum() + prior_weight * prior) / (m.sum() + prior_weight)
    return enc

print("leaky global encoding AUC:", round(roc_auc_score(y, global_encoding(cat, y)), 3))  # ~0.75: fake signal
print("out-of-fold encoding AUC:", round(roc_auc_score(y, oof_encoding(cat, y)), 3))       # ~0.5: honest

Заведи таблицу экспериментов: модель, признаки, CV score, LB score, заметки.

Решение. Минимальные колонки: дата, ID эксперимента (и git commit), модель и ключевые гиперпараметры, набор признаков (версия), схема CV и seed, CV mean ± std, public LB, время обучения, вывод. Правила: менять одну вещь за раз; записывать и неудачные эксперименты; смотреть, коррелирует ли CV с LB по всей таблице (если нет — схема CV не отражает test). Подойдёт CSV/Google Sheets, а удобнее — MLflow или W&B, которые логируют это автоматически.

[Interview] Public vs private

Объясни, почему модель может улучшить public LB, но ухудшиться на private LB.

Решение. Public LB считается на небольшой части test (часто 20–30%), private — на остальной. При малом public наборе score шумный: если перебрать много сабмитов и выбрать лучший по public, мы выбираем в том числе удачный шум — это переобучение на public LB (по сути, multiple comparisons). Пример: при 2000 строк в public стандартная ошибка accuracy около 0.9 ± √(0.09/2000) ≈ ±0.007 — разница между сабмитами в 0.005 неотличима от шума. Кроме того, public и private могут различаться по распределению (другое время, другие сегменты). Защита: выбирать финальные сабмиты по надёжной CV, а не по public; использовать устойчивые ансамбли; проверять, что CV и public коррелируют; помнить, что «shake-up» на private — нормальная вещь для переобученных на public решений.

Проверь себя

Вопросы для самопроверки

  1. Какой стратегии придерживаться в первые дни Kaggle соревнования?

    EDA → baseline submission (простая модель) → понять gap до lb → feature engineering → кросс-валидация. Не тюни гиперпараметры раньше, чем построишь надёжную CV. Часто baseline XGBoost/LightGBM + базовые признаки даёт 80% от финального результата.

  2. Почему Local CV важнее Public Leaderboard при разработке?

    Public LB использует только часть тестовых данных (обычно 20-30%). Переоптимизация под него приводит к shake-up на private LB (финальном). Надёжная кросс-валидация коррелирует с private LB. Правило: доверяй CV, а не public LB.

  3. Что такое «shake-up» на Kaggle и почему он происходит?

    Shake-up — изменение позиций в рейтинге при переходе с public на private LB. Происходит из-за переобучения под public LB (маленькая выборка), случайности в оценке или overfitting к особенностям конкретного сплита. Защита: ансамблирование, стабильная CV, не оптимизировать под public aggressively.

  4. Как строить финальный ансамбль для Kaggle?

    Стратегии: (1) усреднение (soft voting) разных типов моделей (GBM + NN + linear), (2) rank averaging — усреднение рангов предсказаний, (3) stacking — meta-learner на OOF предсказаниях. Ключевое: diverse models с низкой корреляцией ошибок дают лучший ансамбль, чем 10 похожих моделей.

  5. Что такое target leakage и как её обнаружить?

    Утечка — когда признаки содержат информацию о target, недоступную в момент предсказания. Как искать: (1) признак с почти идеальной связью с target; (2) резкое падение score после удаления подозрительного признака; (3) время записи признака — до или после события target? (4) сравнение распределений признаков в train и test — признак, которого нет или который ведёт себя иначе в test, подозрителен.

  6. Зачем стратифицированная кросс-валидация в соревнованиях с дисбалансом?

    При случайном разбиении доля позитивов в фолдах может сильно колебаться, и оценка на миноритарном классе становится шумной. StratifiedKFold сохраняет долю классов в каждом фолде и даёт более стабильную оценку. На маленьких датасетах с очень редким классом случайный сплит может вообще дать фолд почти без позитивов.

Как закрепить тему: Kaggle Competition

Блок связывает теорию с практикой: где применять идею, какие ошибки проверять и как развиваться дальше.

Когда применять

  • Фиксируй CV схему и seed с первого дня — без этого нельзя сравнивать эксперименты.
  • Читай discussion и notebooks лидеров — domain knowledge часто важнее ML.
  • Финальный сабмит: два разных ансамбля на случай shake-up.

Типичные ошибки

  • Оптимизировать под public LB без надёжной CV — высокий риск shake-up на private LB.
  • Тратить всё время на feature engineering без проверки baseline.
  • Делать единственный финальный submission — всегда сохраняй разные варианты.

Что тюнить / проверить

  • CV схема: надёжность важнее correlation с public LB.
  • Ensemble weights: оптимизируй на holdout, не на public LB.
  • Feature selection: permutation importance на OOF предсказаниях.

9.5 Interview Prep — ML System Design

На system design интервью оценивают не знание модной модели, а умение структурировать неопределённую задачу: уточнить цель, оценить масштаб, выбрать данные, построить pipeline, serving и monitoring.

Почему важно

System design для ML — навык, проверяемый в крупных компаниях. Clarify → Estimate → Design → Scale → Monitor — структура, которая работает на любом интервью.

  • Оценка масштаба: QPS, latency, storage — как быстро посчитать
  • Типичные ML systems: recommendation, search, fraud detection
  • Failure modes и monitoring — что спрашивают в конце интервью

Framework ответа

clarify -> metrics -> scale -> data -> model -> serving -> monitoring -> risks

Хороший ответ всегда начинается с уточнений. Нельзя проектировать fraud detection, recommender или RAG одинаково: стоимость ошибки, latency, labels и feedback loop разные.

1. Рекомендательная система

Clarify: что рекомендуем, кому, где показываем, оптимизируем CTR, watch time или retention. Data: impressions, clicks, dwell time, user/item metadata. Model: candidate generation + ranking. Serving: precompute candidates, online ranker. Monitoring: CTR, diversity, freshness, popularity bias.

2. Детекция фрода

Уточнить: real-time или batch, цена false positive и false negative. Данные: транзакции, история пользователя, устройство, мерчант, velocity-признаки. Модель: baseline на gradient boosting, откалиброванный порог. Serving: online-скоринг с низкой latency. Мониторинг: drift, запаздывающие метки, усталость от алертов.

3. Семантический поиск по документам

Уточнить: корпоративные документы, веб-поиск или база знаний поддержки. Данные: документы, chunks, метаданные, логи запросов. Модель: retrieval по эмбеддингам + опциональный cross-encoder reranker. Serving: векторный индекс, гибридный поиск, кеширование. Мониторинг: доля пустых выдач, удовлетворённость по кликам, устаревшие документы.

4. Модерация изображений

Уточнить: категории политики, ручная проверка, допустимые latency и доля false negatives. Данные: размеченные изображения, hard negatives, обновления политики. Модель: классификатор/детектор плюс порог на каждый класс. Serving: асинхронный пайплайн для тяжёлых моделей, правила-fallback. Мониторинг: доля апелляций, drift по источникам контента, расхождения модераторов.

5. LLM-ассистент с RAG

Уточнить: домен, стиль ответов, допустимость галлюцинаций, приватность. Данные: документы, chunks, метаданные, вопросы для оценки. Модель: retriever + reranker + генератор. Serving: переформулировка запроса, поиск, генерация, цитирование. Мониторинг: groundedness, hit rate поиска, latency, обратная связь пользователей.

Как звучать сильно на интервью

  • Всегда называй primary metric и guardrail metrics.
  • Отделяй offline metric от online business impact.
  • Обсуждай feedback loop и delayed labels.
  • Показывай fallback, rollback и human-in-the-loop там, где ошибка дорогая.
  • Не прыгай к Transformer до baseline и data pipeline.

Проверь себя

Вопросы для самопроверки

  1. Как структурировать ответ на вопрос о ML System Design на собеседовании?

    Структура: (1) Clarify requirements — бизнес-цель, масштаб, latency, freshness. (2) Define ML task — что предсказываем, какой лейбл. (3) Data pipeline — сбор, хранение, preprocessing. (4) Feature engineering. (5) Model selection. (6) Evaluation & offline testing. (7) Serving & monitoring.

  2. Что спрашивают при проектировании рекомендательной системы?

    Типичные вопросы: cold start problem (новые пользователи/items), масштаб (миллионы пользователей × миллиарды items), latency (retrieval → ranking → reranking pipeline), diversity vs relevance trade-off, feedback loop bias (popular items получают больше показов → больше clicks).

  3. Что такое two-tower model и когда он применяется?

    Two-tower: отдельные encoders для user и item, скалярное произведение эмбеддингов = relevance score. Позволяет предвычислить item embeddings и делать ANN search при inference. Используется в recommendation (YouTube, Pinterest), search, ad retrieval — везде, где нужно быстро найти релевантные items из миллиардов.

  4. Как объяснить компромисс между precision и recall при проектировании системы?

    Precision vs Recall зависит от стоимости ошибок. В медицинской диагностике FN (пропуск болезни) дороже FP (лишний тест) → высокий recall. В спам-фильтре FP (потеря важного письма) дороже FN (пропуск спама) → высокий precision. Порог выбирается по бизнес-стоимости ошибок.

  5. Какой первый вопрос задать на интервью по ML system design?

    Уточни бизнес-цель до того, как формулировать ML-задачу. Спроси: какое решение поддерживает система, сколько стоит ошибка, какие ожидаются latency и масштаб, какие данные доступны. Без этого нельзя выбрать между online и batch inference, бинарной моделью и ранжированием — и даже понять, нужен ли здесь ML.

  6. Как определить рамки задачи рекомендательной системы?

    Спроси: что рекомендуем (товары, видео, людей), кому, в каком контексте (главная, email, push) и что оптимизируем (CTR, время просмотра, покупки, удержание). Затем уточни масштаб (DAU, размер каталога, частота обновления), определи ML-задачу (ранжирование, retrieval или оба) и найди сигнал обратной связи и задержку меток. Cold-start и popularity bias стоит обсудить до выбора модели.

  7. Какие метрики важны для антифрода, кроме accuracy?

    На сильно несбалансированных данных accuracy почти бесполезна. Важны: recall по фроду (ловим реальный фрод), precision (не блокируем легитимных пользователей), бизнес-матрица стоимости (сколько стоит пропущенный фрод против ложной блокировки), p99 latency (скоринг часто стоит на критическом пути платежа) и усталость команды проверки от алертов. Также следи за качеством по сегментам, чтобы ловить проблемы справедливости.

  8. Чем система ранжирования поиска отличается от рекомендательной?

    Поисковое ранжирование зависит от запроса: пользователь явно сообщает намерение (текст запроса), и оно ограничивает, что искать и ранжировать. Рекомендации работают без запроса: система выводит, что показать, из неявных сигналов (история, контекст, коллаборативная фильтрация). Поиск требует сопоставления запроса с документами (часто BM25 + dense retrieval), рекомендации — моделирования склонности пользователь–объект без явной информационной потребности.

  9. Какова роль reranker-а в RAG-ассистенте?

    Retriever быстро находит большой набор кандидатов (например, top-100 chunks) приближённым поиском ближайших соседей по эмбеддингам. Reranker затем оценивает каждого кандидата более дорогим cross-encoder-ом, который видит запрос и документ вместе, и выбирает top-k самых релевантных chunks для генератора. Без него генератор получает нерелевантные chunks, что ведёт к галлюцинациям и ответам не по теме.

  10. Как справиться с cold-start в новой рекомендательной системе?

    Cold-start бывает двух видов: новый пользователь (нет истории) и новый объект (нет взаимодействий). Для новых пользователей — рекомендации по популярности или по контенту, пока не накопится сигнал, либо явный опрос предпочтений при онбординге. Для новых объектов — метаданные (категория, эмбеддинги описания, цена), чтобы поместить объект в пространство эмбеддингов рядом с похожими. В обоих случаях помогает exploration (epsilon-greedy или Thompson sampling), чтобы быстрее собрать обратную связь.

Как закрепить тему: System Design на собеседовании

Блок связывает теорию с практикой: где применять идею, какие ошибки проверять и как развиваться дальше.

Когда применять

  • Используй фреймворк: clarify → data → features → model → eval → serving → monitoring.
  • Всегда спрашивай о масштабе: DAU, латентность, freshness требований.
  • Бэк-оф-нэпкин расчёты — обязательная часть: сколько QPS, памяти, GPU.

Типичные ошибки

  • Прыгать к архитектуре без уточнения требований.
  • Называть «лучшую модель» без обоснования trade-off.
  • Игнорировать monitoring и model degradation — это признак опыта, когда упоминаешь.

Что тюнить / проверить

  • Широта vs глубина ответа: фреймворк первым, детали по запросу интервьюера.
  • Акцент на trade-offs: latency/throughput, precision/recall, cost/quality.
  • Примеры из практики — сразу повышают убедительность ответа.
